# 登录校验与只读 SQL 编辑修复设计

## 目标

修复登录表单本地校验失败时出现错误登录提示的问题，并确保模型步骤中的用户 SQL 可以正常输入、回显和保存，但任何保存、校验或执行入口都只接受一条可解析的只读 `SELECT`。

## 方案选择

1. 仅前端拦截：交互反馈直接，但接口可被绕过，不采用。
2. 仅后端拦截：安全边界可靠，但用户只能在提交后得到反馈，不采用。
3. 前后端纵深防护：前端提供及时提示，后端作为不可绕过的最终边界，采用此方案。

## 登录行为

- Element Plus 表单校验失败时立即结束提交流程。
- 用户名、密码或验证码为空时，只显示对应字段的内联校验消息。
- 验证码为空时显示“请输入验证码”，不显示“登录失败，请检查用户名和密码”，也不刷新验证码。
- 只有表单校验通过并实际调用登录接口后，接口错误才显示登录错误消息并刷新验证码。

## SQL 编辑、保存与执行

- Monaco SQL 编辑器继续允许自由输入和修改文本，不在键入阶段删除或阻止关键字。
- 步骤最终“保存”前调用现有 SQL 校验接口；空 SQL或不安全 SQL 不提交，并显示后端返回的具体原因。
- “保存&关闭”仍允许只保存步骤基本信息和空 SQL，作为未完成草稿。
- 后端在新增、插入、更新步骤时，对非空 `sqlStatement` 使用现有 `ReadOnlySqlGuard` 校验并保存规范化 SQL。
- 后端在执行步骤前再次使用 `ReadOnlySqlGuard` 校验，删除执行用户 DML/DDL 的分支。
- 用户 SQL 只允许一条可解析的 `SELECT`，包括以 `WITH` 开头的查询；拒绝 `DELETE`、`UPDATE`、`INSERT`、`TRUNCATE`、`CREATE`、`ALTER`、堆叠语句、文件读取和延时函数。
- 系统为保存查询结果而生成的内部结果表 DDL 不属于用户 SQL，保持现有行为。

## 数据流

1. 用户在 SQL 编辑器输入 SQL。
2. 编辑器状态通过 `QueryEditor` 暴露给步骤编辑弹窗。
3. 用户点击最终“保存”时，前端先调用 `/api/v1/sql/validate`。
4. 校验成功后调用步骤新增/更新接口。
5. 后端从步骤配置提取 SQL，并再次通过 `ReadOnlySqlGuard` 后才持久化。
6. 执行步骤时，后端重新校验已保存 SQL，再使用系统生成的结果表语句执行该只读查询。

## 错误处理

- 表单本地校验错误不进入登录接口错误处理。
- SQL 为空时提示“请先输入 SQL 语句”。
- SQL 不是单条只读查询时，保存和执行均返回明确业务错误，不执行数据库操作。
- 后端校验是最终安全边界，不能依赖前端拦截。

## 测试与验证

- 浏览器红绿验证：用户名和密码有效、验证码为空时，修复前出现错误登录 toast；修复后只显示“请输入验证码”。
- 后端单元测试：步骤新增/更新拒绝修改型或堆叠 SQL；步骤执行在访问数据源和异步执行前拒绝不安全 SQL；合法 `SELECT` 仍可保存。
- 回归运行全部后端测试和 Maven 打包。
- 运行前端 `npm run build`。
- 浏览器验证登录提示、SQL 编辑器输入、合法 SQL 保存路径和非法 SQL 保存拦截。

## 范围外事项

- 不引入 Hive 方言、异步查询取消、分页结果或新的 SQL 编辑器功能。
- 不改变系统内部结果表的命名和物化逻辑。
- 本轮不合并、不推送、不创建 Git 提交。
