# README 与默认管理员初始化优化设计

## 背景

当前 README 的 API 文档仍使用旧的 `/api/**` 路径，未覆盖最新 SQL 只读约束、前端发布构建和实际 CORS 配置方式。本地数据源文件的生成方式也不够明确，容易让使用者误以为仓库缺少配置文件。

更严重的是，MySQL 初始化脚本把默认管理员密码 `admin123` 以明文写入 `sys_user`，但登录服务只使用 BCrypt 校验。全新数据库按 README 初始化后，默认账号无法正常登录，同时明文密码不符合当前安全基线。

## 目标

1. 让全新 MySQL 数据库初始化出的开发管理员能够通过 BCrypt 登录。
2. 不覆盖既有数据库中的管理员账号或密码。
3. 让 README 与当前运行配置、API 路径和 SQL 安全行为保持一致。
4. 明确默认账号只能用于本地开发，生产环境不得使用。
5. 保留用户当前对 README 后端配置章节的已有修改，并在其基础上完善说明。

## 非目标

- 不新增修改密码接口或用户管理页面。
- 不自动迁移既有数据库中的明文密码。
- 不把本机 `datasource-local.yml` 或任何真实凭证加入 Git。
- 不修改现有 API 行为、SQL Guard 规则或 CORS 实现。

## 默认管理员初始化

`backend/src/main/resources/schema-mysql.sql` 继续使用 `INSERT IGNORE` 创建开发管理员：

- 用户名保持为 `admin`。
- 开发初始密码保持为 `admin123`。
- SQL 中保存一个由 Hutool BCrypt 生成、且能够通过 `BCrypt.checkpw("admin123", hash)` 校验的固定 BCrypt 哈希，不再保存明文密码。
- `INSERT IGNORE` 保证重复执行初始化脚本时不会覆盖已有 `admin` 记录。

已有数据库不会因本次变更自动更新。如果旧记录仍保存明文密码，应在数据库外安全生成新的 BCrypt 哈希，再由管理员单独更新该记录；不得在提交、日志或聊天中传递生产密码。

## 自动化验证

新增一个后端单元测试读取 `schema-mysql.sql` 的默认管理员插入语句：

1. 提取保存到 `password` 字段的值。
2. 断言该值不是 `admin123`。
3. 断言该值具有 BCrypt 格式。
4. 断言 Hutool `BCrypt.checkpw("admin123", hash)` 返回 `true`。

测试先在当前明文脚本上失败，再替换哈希并验证通过。

## README 调整

### 快速开始与数据源配置

- 明确 `backend/config/datasource-local.yml` 默认不存在。
- 给出从 `datasource-local.example.yml` 复制创建的 PowerShell 命令。
- 说明该文件被 Git 忽略，真实凭证只能保存在本机。
- 以本地文件作为主要开发配置方式，同时保留进程环境变量作为可选方案。
- 说明后端从 `backend` 目录启动时，`./config/datasource-local.yml` 才能解析到正确位置。

### 默认账号

- 保留 `admin/admin123`，但明确仅用于本地开发和全新数据库。
- 明确生产环境不得使用该默认账号，部署前必须修改密码或禁用/删除默认账号。
- 说明 `INSERT IGNORE` 不会重置已有管理员密码。

### API 文档

- 认证路径改为 `/api/v1/auth`，补充刷新令牌接口并注明当前未实现。
- 模型路径改为 `/api/v1/models`，补充状态更新。
- 步骤路径改为 `/api/v1/models/{modelId}/steps`，修正执行路径并补充详情、插入、排序、交换、树和结果接口。
- 元数据路径改为 `/api/v1/metadata`，补充连接检查、表详情、搜索、行数和预览接口。
- 新增 `/api/v1/sql` 章节，列出校验、执行、解析、生成、智能推荐和关联关系接口。
- 标明除验证码、登录和刷新令牌等公开认证入口外，数据 API 均需有效令牌。

### SQL 安全行为

新增说明：

- SQL 编辑器支持输入、保存和重新编辑回显。
- 校验、最终保存和执行只允许一条可解析的只读 `SELECT`，包括 `WITH ... SELECT`。
- 拒绝 DML、DDL、堆叠语句、文件读取和延时函数。
- 同步预览默认 50 行、硬上限 1000 行、查询超时 60 秒。
- “保存&关闭”仍允许保存空白草稿。

### 发布门禁与 CORS

- 在后端测试和打包之外，加入前端 `npm ci` 和 `npm run build`。
- 给出 `FRONTEND_ORIGIN` 的生产配置示例。
- 保留未知 Origin 不返回允许头、不得使用凭证通配 CORS 的要求。
- 数据库凭证轮换状态只有在旧凭证确认失效后才能标记完成。

## 验证

实施完成后执行：

1. 新增初始化账号测试的红绿验证。
2. `mvn test`，确认完整后端测试通过。
3. `mvn package -DskipTests`，确认后端可打包。
4. `npm run build`，确认前端类型检查和生产构建通过。
5. `git diff --check`，确认 Markdown 与 SQL 差异无格式错误。
6. 检查 Git 状态，确认 `backend/config/datasource-local.yml` 继续被忽略，且没有任何真实凭证进入差异。

## 风险与边界

公开的开发默认密码即使以 BCrypt 保存也不能用于生产。README 的警告只能降低误用风险，无法代替首次登录强制改密功能。后续如需正式部署，应另行设计管理员引导、强制改密或一次性初始化令牌机制。
